# INUWIKI 部署说明

> 适用版本：2026-11-16 之后的 WIKI 代码  
> 目标环境：Ubuntu 22.04 + Nginx + PHP-FPM 8.x + OPcache + Redis + Supervisor  
> 部署形态：见下方「部署形态二选一」。  
> 本文件是独立部署说明；`deploy/README.md` 保留作历史运维备忘，若两者冲突，以本文件为准。

### 部署形态二选一

WIKI 前端用 `createWebHistory()`、vite 未设 `base`，接口前缀固定为同源 `/kbapi`。据此有两种部署形态，**任选其一，不要混用**：

| 形态 | 端口 | 前端路径 | Nginx 关键配置 | 适用 |
|---|---|---|---|---|
| A. 独立端口（推荐） | WIKI 独占一个对外端口（例 8081） | 站点根 `/` | `root` 指向 `frontend/dist`；`location /kbapi/` 反代到 PHP-FPM；`location /` 做 history 回退 | 已有 EIP 占用其它端口、或防火墙只放行特定端口 |
| B. 单域名路径分发 | 与 EIP 共用 80/443 | `/kb/` 子路径 | `alias` 指向 `frontend/dist`；前端须用 `--base=/kb/` 重新构建，否则静态资源 404 | 强制单域名单端口 |

形态 B 必须在**构建前端时**带上 base：`npm run build -- --base=/kb/`，否则 `dist/index.html` 里的 `/assets/...` 绝对路径在 `/kb/` 下会 404。形态 A 无需此步骤。

下文命令默认以形态 A（独立端口 8081、代码目录 `~/INUGAME/INUWIKI`）为例；若用形态 B 或标准目录 `/var/www/inuwiki`，按第 4 节的说明替换路径与端口。

## 1. 部署形态与目录

> 下列 `/var/www/inueip`、`/var/www/inuwiki` 是**标准目录示例**。实际部署可不落在 `/var/www`（如 `~/INUGAME/INUEIP`、`~/INUGAME/INUWIKI`），把全文相应路径替换即可；**关键是全文前后一致**，且 Nginx/supervisor/FPM 配置里的路径与之一致。

| 路径（示例） | 用途 |
|---|---|
| `/var/www/inueip/backend` | 现有 INUEIP 后端 |
| `/var/www/inueip/frontend/dist` | 现有 INUEIP 前端产物 |
| `/var/www/inuwiki/backend` | WIKI 后端 |
| `/var/www/inuwiki/frontend/dist` | WIKI 前端构建产物 |
| `/data/inuwiki` | WIKI 媒体与上传根目录，建议独立挂载 |
| `/var/log/supervisor/kb-worker.log` | WIKI 队列 Worker 日志 |
| `/var/www/inuwiki/backend/runtime/oplog` | 操作日志文件日志目录，必须可写 |

Nginx 路径规则（**形态 B 单域名**示例；形态 A 独立端口下 WIKI 前端在根 `/`、后端仍是 `/kbapi/`，见 4.4.1）：

| 路径 | 指向 |
|---|---|
| `/` | INUEIP 前端静态产物 |
| `/api/` | INUEIP PHP-FPM |
| `/kb/` | WIKI 前端静态产物 |
| `/kbapi/` | WIKI PHP-FPM |
| `/internal-media/` | 仅允许 WIKI 后端通过 `X-Accel-Redirect` 内部访问 |
| `/uploads/knowledge/`、`/kbuploads/` | 禁止外部直出，统一走 `/kbapi/assets` 鉴权 |

容量建议：单视频上限 1GB；50 个视频约 30–50GB；`/data/inuwiki` 建议不小于 200GB。

## 2. 环境与依赖

### 2.1 PHP 版本与扩展

代码要求 PHP ≥ 8.0（ThinkPHP 8）。**版本不必锁死 8.2**，但必须做到「CLI、FPM、扩展三者一致」。先确认机器上有哪些版本、哪个在跑：

```bash
php -v | head -1
ls -d /etc/php/*/fpm/pool.d 2>/dev/null
systemctl is-active php8.2-fpm php8.5-fpm 2>/dev/null
```

按实际版本安装扩展（把 `8.2` 换成你要用的版本，例如 `8.5`）：

```bash
sudo apt update
sudo apt install -y nginx redis-server supervisor ffmpeg \
  php8.2-fpm php8.2-mysql php8.2-redis php8.2-mbstring \
  php8.2-xml php8.2-curl php8.2-gd php8.2-imagick php8.2-zip
```

确认关键扩展在 **FPM 用的那个版本**里存在（队列依赖 redis，缺了会 500）：

```bash
php8.2 -m | grep -E 'pdo_mysql|redis|mbstring'
```

> 踩坑：机器上可能同时装有 8.1/8.2/8.5 多个 FPM，且各自扩展不同（例如 8.2 没装 redis、8.5 有）。务必让 Nginx `fastcgi_pass` 指向的 socket 所属版本带齐扩展，否则页面能出、接口 500。

### 2.2 Composer

系统 apt 包安装的 Composer 通常版本较旧，在 PHP 8.4/8.5 下会刷出大量 `Deprecated` / `E_STRICT deprecated` 警告——这些**不是错误，不影响安装**，可忽略。若想根治，用官方安装器替换为最新版：

```bash
sudo apt remove -y composer
php -r "copy('https://getcomposer.org/installer', 'composer-setup.php');"
php composer-setup.php --install-dir=/usr/local/bin --filename=composer
rm -f composer-setup.php
composer --version
```

### 2.3 依赖安装与权限

后端依赖（**必须在 backend 目录内执行**，否则报 `could not find a composer.json file`）：

```bash
cd /var/www/inuwiki/backend        # 或你的实际代码目录
composer install --no-dev --optimize-autoloader
ls -l vendor/autoload.php          # 确认生成
```

> 踩坑 1：直接跑 `php think migrate:run` 报 `Failed opening required .../vendor/autoload.php`，是因为**漏了 `composer install`**，先装依赖再迁移。
> 踩坑 2：`vendor does not exist and could not be created` 是当前用户对项目目录**没有写权限**。修复属主后再装：`sudo chown -R <部署用户>:<部署用户> /path/to/INUWIKI`。全程用同一个用户操作，避免 root 装完、普通用户后续无权限覆盖。
> 踩坑 3：root 执行 Composer 需加 `COMPOSER_ALLOW_SUPERUSER=1` 跳过交互，但生成的 `vendor/` 属主是 root，之后要 chown 回部署用户。

前端依赖与构建：

```bash
cd frontend
npm ci
npm run build
# 形态 B（/kb/ 子路径）需改成：npm run build -- --base=/kb/
```

`npm run build` 会执行 `vue-tsc -b && vite build`，并打包历史版本差异所需的 `diff` 依赖。生产环境只需要分发 `frontend/dist/`。

> 踩坑：本地 `frontend/dist/` 被 `.gitignore` 忽略，部署机若用 `git pull` 是**拿不到 dist 的**。要么在部署机上 `npm ci && npm run build`，要么用 rsync/scp 分发，或用临时分支强制提交 dist 后再检出（见 9.x）。绝不能假设 pull 会带上前端产物。

## 3. 配置文件

### 3.1 `.env`

从 `backend/.env.example` 复制：

```bash
cp /var/www/inuwiki/backend/.env.example /var/www/inuwiki/backend/.env
```

生产环境要点：

```ini
APP_DEBUG = false

# EIP 库：只读账号，仅用于用户、角色、权限读取
EIP_DB_HOST = 127.0.0.1
EIP_DB_NAME = INUEIP
EIP_DB_USER = eip_readonly
EIP_DB_PASS = <readonly-password>
EIP_DB_PORT = 3306
EIP_DB_PREFIX = inue_

# WIKI 库：读写账号
KB_DB_HOST = 127.0.0.1
KB_DB_NAME = Inuwiki
KB_DB_USER = <wiki-user>
KB_DB_PASS = <wiki-password>
KB_DB_PORT = 3306
KB_DB_PREFIX =

QUEUE_CONNECTION = redis

# JWT 回落密钥；主配置仍以 myconfig.jwt.secret 为准
JWT_SECRET = <random-64-char-string>
```

数据库连接只从 `.env` 读取。

#### 3.1.1 EIP 库账号：运行时只读 + 迁移临时可写（关键）

EIP 库需要**两个不同阶段、两种权限**的账号，不要混淆：

| 阶段 | 用途 | 所需权限 | 说明 |
|---|---|---|---|
| 运行时（常态） | 登录校验、用户/角色/权限读取、目录快照同步 | `SELECT`（只读） | 业务代码严禁写 EIP 库，`.env` 平时应配只读账号 |
| 首次迁移（一次性） | `SeedKbPermissions` 等迁移要向 `INUEIP.inue_permission` 注册 `kb:*` 权限点 | `SELECT, INSERT, UPDATE, DELETE`（仅这一次） | 项目**唯一**写 EIP 库的地方，迁移时必须临时用可写账号 |

> 错误认知："EIP 库严禁使用可写账号，迁移也用只读账号"。这样会在第 3 条迁移 `20260926000300 SeedKbPermissions` 报 `SQLSTATE[HY000] [1044] Access denied for user 'eip_readonly' to database 'INUEIP'`（只读账号无写权限），后续 14 条迁移全部 `down`，`kb_subject` 等表建不出来，`kb:subject-sync` 随之报 `Table 'Inuwiki.kb_subject' doesn't exist`。

**正确做法**：

1. 准备只读账号（运行时用）并授权：

```sql
sudo mysql -u root -p        # 若 root 是密码认证；`sudo mysql` 无密码报 1045 时改用此方式
-- 先确认库名大小写一致（Linux 区分大小写）
SHOW DATABASES LIKE 'INUEIP';
SELECT user, host FROM mysql.user WHERE user='eip_readonly';
GRANT SELECT ON INUEIP.* TO 'eip_readonly'@'localhost';   -- host 按上面查到的填（localhost / %）
FLUSH PRIVILEGES;
```

> 踩坑：只 `GRANT SELECT` 还不够——若 `eip_readonly` 对 `INUEIP` 库**完全没有授权**，`kb:subject-sync` 也会报 1044（"认证通过但无库权限"）。1044 是权限问题，1045 是密码/认证问题，区分开。

2. 建迁移专用可写账号（仅迁移时用）：

```sql
CREATE USER IF NOT EXISTS 'kb_migrate'@'localhost' IDENTIFIED BY '<密码>';
GRANT SELECT, INSERT, UPDATE, DELETE ON INUEIP.* TO 'kb_migrate'@'localhost';
FLUSH PRIVILEGES;
```

3. 迁移期间把 `.env` 的 `EIP_DB_USER/PASS` 临时改为 `kb_migrate`，跑完 `php think migrate:run` 后**立即改回 `eip_readonly`**（见 4.3）。迁移脚本幂等（按 `code` 判重），重复跑不会插重复权限点。

4. 迁移完成后验证权限点已入库：

```bash
sudo mysql -u root -p -e "SELECT code FROM INUEIP.inue_permission WHERE code LIKE 'kb:%';"
```

### 3.2 `backend/config/myconfig.php`

`myconfig.php` 是 WIKI 的唯一业务配置源。生产环境需重点确认：

| 分组 | 必须确认项 |
|---|---|
| `deploy` | `env=production`；`api.base_url`、`web.base_url`、`eip.base_url` 为真实地址（含实际端口，如 `http://1.117.67.247:8081/kbapi`）；`cors.allow_origin` 填前端实际来源、不允许填 `*` |

> 踩坑：`deploy.api.base_url` / `web.base_url` 默认还是 `127.0.0.1:8001` / `5174`，不改会跳回本地地址。三个 URL 的**协议+IP+端口**必须与浏览器实际访问的一致；`api.base_url` 一般以 `/kbapi` 结尾。前端在运行时通过 `GET /kbapi/config` 拉取这些值（白名单下发），改完 reload PHP-FPM 后可访问该接口验证。
>
> `cors.allow_origin` 在形态 A（同源）下可填前端同地址，形态 B 单域名下填同一域名；切勿用 `*`。
| `jwt` | `secret` 替换为随机 64 位字符串；与 `.env JWT_SECRET` 保持一致或同时替换 |
| `upload` | `root=/data/inuwiki`；`url_prefix=/uploads`；后台页脚磁盘统计读取该目录所在文件系统 |
| `knowledge` | `upload_prefix=/uploads/knowledge`；`chunk_size` 与 Nginx `client_max_body_size` 匹配；`version_keep` 符合保留要求 |
| `media` | `internal_prefix=/internal-media`，必须与 Nginx internal location 一致 |
| `ffmpeg` | `bin=/usr/bin/ffmpeg`，`ffprobe=/usr/bin/ffprobe` |
| `trash` | `retention_days=30`；`temp_retention_hours=24` |
| `oplog` | `db_enabled=true`；`trusted_proxies` 按需配置额外可信代理 |
| `log_gc` | `retention_days=180`；`max_total_mb=512` |

禁止加入 `frontend_public.keys` 的分组：`database`、`jwt`、`oplog`、`log_gc`。

后台知识管理页脚的统计来自只读接口 `GET /kbapi/admin/kb/stats`：

| 字段 | 口径 |
|---|---|
| `used_bytes` / `total_bytes` | `upload.root` 所在文件系统的已用 / 总容量 |
| `transcoding` | `kb_attachment.status` 为 `pending` / `merging` / `transcoding` 的数量 |
| `failed` | `kb_attachment.status` 为 `failed` 的数量 |

接口只返回聚合数字，不返回绝对路径、附件名或失败原因。统计接口不可用时，前端显示占位值而不阻断列表页。

### 3.3 操作日志 IP 可信代理

应用默认信任本机回环代理。若链路为：

```text
浏览器 -> 前置代理 / 负载均衡 -> Nginx -> PHP-FPM
```

且前置代理不在本机，需要在 `myconfig.oplog.trusted_proxies` 中配置前置代理 IP 或 CIDR：

```php
'oplog' => [
    'trusted_proxies' => ['10.0.0.5/32'],
],
```

该配置是追加，不会覆盖默认的 `127.0.0.0/8`、`::1/128`。

同时必须保证前置代理和 Nginx 透传：

- `X-Real-IP`
- `X-Forwarded-For`

否则操作日志仍可能记为 `127.0.0.1`。

## 4. 首次部署步骤

> 下列命令以形态 A（独立端口 8081、代码目录 `~/INUGAME/INUWIKI`、PHP 8.5）为例。若用标准目录 `/var/www/inuwiki`，把路径替换即可；PHP 版本按 2.1 实际确认的版本替换。**全文路径与版本必须前后一致**。先定义一个变量减少出错：

```bash
KB_ROOT=/home/ubuntu/INUGAME/INUWIKI      # 改成你的实际路径
FPM_VER=8.5                               # 改成实际的 PHP-FPM 版本
```

### 4.1 部署代码

推荐：在本地或 CI 构建前端，生产机只接收后端代码与 `dist`（dist 不会被 git pull 带下来，见 2.3）。

```bash
sudo mkdir -p "$KB_ROOT" /data/inuwiki

sudo rsync -a --exclude=runtime --exclude=node_modules backend/ "$KB_ROOT/backend/"
sudo rsync -a frontend/dist/ "$KB_ROOT/frontend/dist/"
```

`backend/runtime` 不随代码分发，需手动创建并赋权。属主应与运行 FPM/Worker 的用户一致（下面以 `ubuntu` 为例；若 FPM 池用 `www-data`，改成 `www-data`）：

```bash
sudo mkdir -p "$KB_ROOT/backend/runtime/oplog"
sudo chown -R ubuntu:ubuntu "$KB_ROOT" /data/inuwiki
sudo chmod -R 755 /data/inuwiki
```

> 踩坑：`supervisor/kb-worker.conf` 模板里是 `user=www-data`，但代码目录属主可能是 `ubuntu`。二者不一致会导致 worker 写日志/缓存失败。要么把 worker 的 `user` 改成与代码属主一致，要么统一 chown 到 `www-data`。以实际能写 `runtime/` 为准。

### 4.2 后端依赖与配置

```bash
cd "$KB_ROOT/backend"
composer install --no-dev --optimize-autoloader
cp .env.example .env
# 按第 3 节修改 .env 与 config/myconfig.php
```

### 4.3 建库与迁移

建库（注意 MySQL 认证方式：若 `sudo mysql` 无密码报 `ERROR 1045 ... using password: NO`，说明 root 已改为密码认证，改用 `sudo mysql -u root -p`）：

```bash
sudo mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS Inuwiki DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
```

按 3.1.1 准备好只读账号与迁移账号后，**迁移期间临时切成可写账号**：

```bash
cd "$KB_ROOT/backend"

# 1) 临时把 .env 的 EIP_DB_USER/PASS 改为 kb_migrate（迁移要写 inue_permission）
#    可用 sed 或直接编辑，例如：
#    EIP_DB_USER = kb_migrate
#    EIP_DB_PASS = <密码>

# 2) 跑迁移
php think migrate:run

# 3) 立即改回只读账号 eip_readonly，再做只读取证与同步
php think migrate:status
php think kb:subject-sync
php think kb:asset-bind
```

当前共 17 个迁移，重点包括：

- 空间、内容、权限种子、文章阅读者、人员目录快照、文档类型等基础表；
- 回收站字段与 `kb_article_version`；
- `kb_permission_grant` 与空间范围；
- `operation_log` 分区表；
- `kb:oplog:view` 先加后撤，最终操作日志对所有登录用户可见；
- `operation_log.object_type`，用于区分文章、空间、人员、角色等对象类型。

迁移执行后确认（17 条全部 `up`）：

```bash
php think migrate:status
sudo mysql -u root -p -e "SHOW COLUMNS FROM Inuwiki.operation_log LIKE 'object_type';"
```

> 踩坑：若第 3 条 `SeedKbPermissions` 失败，后面 14 条会全部停在 `down`，`kb_subject` 表不存在，`kb:subject-sync` 报 `Table 'Inuwiki.kb_subject' doesn't exist`。根因就是没按要求临时用可写账号——见 3.1.1。不要在这里改代码或跳过迁移。

### 4.4 部署服务配置

> 文件都在**项目根目录的 `deploy/`** 下。先 `cd` 到项目根目录再 cp，否则报 `cannot stat 'deploy/...'`。

```bash
cd "$KB_ROOT"
sudo cp deploy/nginx/inuwiki.conf        /etc/nginx/conf.d/inuwiki.conf
sudo cp deploy/php-fpm/inuwiki.conf      /etc/php/$FPM_VER/fpm/pool.d/inuwiki.conf
sudo cp deploy/php/opcache.ini           /etc/php/$FPM_VER/fpm/conf.d/10-opcache.ini
sudo cp deploy/supervisor/kb-worker.conf /etc/supervisor/conf.d/kb-worker.conf
```

拷贝后**必须按实际环境改这些模板**，否则服务起不来：

1. **FPM 池**（`/etc/php/$FPM_VER/fpm/pool.d/inuwiki.conf`）：模板监听 `/run/php/php8.2-fpm.sock`，会和该版本的 `www` 池抢同一 socket。给 WIKI 独立 socket，例如 `/run/php/php$FPM_VER-fpm-inuwiki.sock`；`user/group` 与代码目录属主一致。
2. **Supervisor**（`/etc/supervisor/conf.d/kb-worker.conf`）：模板写死 `/var/www/inuwiki/...` 和 `user=www-data`，改成实际 `$KB_ROOT` 与代码属主。确认 supervisor 已安装（`sudo apt install -y supervisor`），否则 `/etc/supervisor/conf.d/` 不存在。
3. **Nginx**：仓库里的 `deploy/nginx/inuwiki.conf` 是**形态 B**（单域名 `/kb/` 子路径）模板。形态 A 需按 4.4.1 改写为「独立端口 + 根路径」。

Nginx/FPM 配置里以下两行不可删除（操作日志记录真实客户端 IP 的关键）：

```nginx
fastcgi_param HTTP_X_REAL_IP $remote_addr;
fastcgi_param HTTP_X_FORWARDED_FOR $proxy_add_x_forwarded_for;
```

> 踩坑：端口冲突。先用 `sudo ss -tlnp | grep ':8081 '` 确认对外端口没被占用；若 80 被 Apache 占用而你又选形态 B，需先停 Apache。形态 A 用独立端口则互不干扰，防火墙放行该端口即可。

#### 4.4.1 形态 A：独立端口 + 根路径的 Nginx 配置

形态 A 下 WIKI 独占一个端口，前端在根路径 `/`，API 走同源 `/kbapi`。**ThinkPHP 路由靠 `s` 参数传递**，`location /kbapi/` 必须用 `rewrite ... ?s=...`，仅 `try_files` 不传 `s` 会导致所有接口 404。

将 `/etc/nginx/conf.d/inuwiki.conf` 写成（`$KB_ROOT`/`$FPM_VER`/端口按实际替换）：

```nginx
upstream kb_fpm {
    server unix:/run/php/php8.5-fpm-inuwiki.sock;    # 与 4.4 FPM 池监听地址一致
}

server {
    listen 8081 default_server;                       # 对外端口，防火墙需放行
    server_name 1.117.67.247;                         # 换成你的 IP/域名

    root /home/ubuntu/INUGAME/INUWIKI/frontend/dist;  # 前端产物根目录
    index index.html;

    client_max_body_size 12m;       # 与 myconfig.knowledge.chunk_size 联动
    client_body_timeout 120s;
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
    add_header X-Content-Type-Options nosniff always;

    # WIKI 后端：必须用 s 参数传 ThinkPHP 路由，否则接口全 404
    location /kbapi/ {
        if (!-e $request_filename) {
            rewrite ^(.*)$ /kbindex.php?s=/$1 last;
        }
    }
    location = /kbindex.php {
        include fastcgi_params;
        fastcgi_pass kb_fpm;
        fastcgi_param SCRIPT_FILENAME /home/ubuntu/INUGAME/INUWIKI/backend/public/index.php;
        fastcgi_read_timeout 120s;
        # 操作日志真实 IP（关键，勿删）
        fastcgi_param HTTP_X_REAL_IP $remote_addr;
        fastcgi_param HTTP_X_FORWARDED_FOR $proxy_add_x_forwarded_for;
        # include fastcgi_params 已提供 REQUEST_SCHEME / HTTPS，
        # 后端据真实协议判定 cookie 是否带 Secure（见 9.12）
    }

    # 禁止媒体直出，统一走鉴权
    location ^~ /uploads/knowledge/ { return 404; }
    location ^~ /kbuploads/         { return 404; }

    # 内部媒体：与 myconfig.media.internal_prefix 一致
    location /internal-media/ {
        internal;
        alias /data/inuwiki/;
        sendfile on;
        sendfile_max_chunk 2m;
        add_header Accept-Ranges bytes;
    }

    # 前端 history 路由回退（SPA 刷新子路由不 404）
    location / { try_files $uri $uri/ /index.html; }

    location ~ /\. { deny all; }
    location ~* \.(sql|bak|old|swp)$ { deny all; }
}
```

配好 `sudo nginx -t` 通过后，用下面的方式自测（应分别返回 200 和 `{"code":0,...}`）：

```bash
curl -sI http://127.0.0.1:8081/ | head -3
curl -s  http://127.0.0.1:8081/kbapi/config
```

> 踩坑：`curl` 返回的 `Server:` 头能识别请求落到哪个服务。若返回 `Apache/2.x` 而不是 `nginx`，说明端口被 Apache 占用、nginx 没监听上，`nginx -t` 虽通过但配置未生效。先解决端口冲突再测。

### 4.5 启动服务

```bash
systemctl is-active redis-server >/dev/null || sudo systemctl start redis-server

sudo nginx -t && sudo systemctl reload nginx
sudo systemctl restart php$FPM_VER-fpm
sudo supervisorctl reread && sudo supervisorctl update
sudo supervisorctl start kb-worker:*
```

> 踩坑：`supervisorctl status` 不加 sudo 可能报 `PermissionError .../xmlrpc.py`。用 `sudo supervisorctl status kb-worker:*` 验证，进程 RUNNING 即正常。

### 4.6 配置定时任务

```bash
cat <<'CRON' | sudo crontab -
*/10 * * * * cd /home/ubuntu/INUGAME/INUWIKI/backend && /usr/bin/php think kb:subject-sync
0 3 * * * cd /home/ubuntu/INUGAME/INUWIKI/backend && /usr/bin/php think kb:gc
0 4 * * * cd /home/ubuntu/INUGAME/INUWIKI/backend && /usr/bin/php think kb:log-gc >> /dev/null 2>&1
10 3 1 * * cd /home/ubuntu/INUGAME/INUWIKI/backend && /usr/bin/php think oplog:maintain >> /dev/null 2>&1
CRON
```

命令说明：

| 命令 | 作用 |
|---|---|
| `kb:subject-sync` | 每 10 分钟同步 EIP 角色 / 人员目录快照 |
| `kb:gc` | 每日清理暂存分片与回收站，默认保留 30 天 |
| `kb:log-gc` | 每日清理运行日志与操作日志文件，默认 180 天、512MB 上限 |
| `oplog:maintain` | 每月维护 `operation_log` 分区，补未来 6 个月，DROP 180 天前旧分区 |

演练命令（**必须先 cd 到 backend**，否则报 `Could not open input file: think`）：

```bash
cd /home/ubuntu/INUGAME/INUWIKI/backend
php think kb:log-gc --dry-run
php think oplog:maintain --dry-run
```

## 5. 更新流程

OPcache 配置中 `validate_timestamps=0`，代码更新后必须 reload PHP-FPM，否则线上仍执行旧代码。以下步骤按“可照抄执行”的顺序整理。

> 本章及后续章节的命令示例沿用**标准目录 `/var/www/inuwiki` 与 PHP 8.2**。若首次部署用了自定义路径/版本（如 `~/INUGAME/INUWIKI`、8.5），执行时把所有 `/var/www/inuwiki` 换成实际路径、`php8.2-fpm` 换成实际版本（如 `php8.5-fpm`）。涉及数据库迁移的更新，**同样遵守 3.1.1 的账号切换规则**（迁移时临时可写、完成后改回只读）。

### 5.1 更新前确认

1. 阅读 `CHANGELOG.md`，确认本次是否包含数据库迁移、配置新增、队列代码或前端改动。
2. 记录当前迁移状态与磁盘余量：

```bash
cd /var/www/inuwiki/backend
php think migrate:status
df -h /data/inuwiki
```

3. 备份代码与数据库。涉及迁移时数据库备份必做：

```bash
TS=$(date +%F-%H%M)
sudo mkdir -p /backup/inuwiki

sudo cp -a /var/www/inuwiki/backend /var/www/inuwiki/backend.prev.$TS
sudo cp -a /var/www/inuwiki/frontend/dist /var/www/inuwiki/frontend/dist.prev.$TS

mysqldump -u <db-user> -p Inuwiki | sudo tee /backup/inuwiki/inuwiki_$TS.sql > /dev/null
```

4. 若修改过 Nginx / PHP-FPM / Supervisor 配置，先备份：

```bash
sudo cp /etc/nginx/conf.d/inuwiki.conf /etc/nginx/conf.d/inuwiki.conf.bak
```

### 5.2 在服务器上通过 Git 更新（推荐）

如果已经在服务器上 `git pull`，代码已经在目标目录，**不要再执行 rsync**。报错 `change_dir ".../backend/backend" failed` 的原因通常是当前目录已经在 `backend/`，相对源路径 `backend/` 被拼成了 `backend/backend/`。

正确流程：

```bash
# 0. 先备份本地配置，避免 git pull 覆盖手工修改
cd /var/www/inuwiki
cp backend/.env /tmp/.env.bak
cp backend/config/myconfig.php /tmp/myconfig.php.bak

# 1. 拉取代码
git pull --ff-only

# 2. 检查配置差异；仓库新增配置键时手工补回生产配置
git diff -- backend/config/myconfig.php

# 3. 后端依赖
cd backend
composer install --no-dev --optimize-autoloader

# 4. 数据库结构变更时执行
php think migrate:run
php think migrate:status

# 5. 前端二选一：
#    A. 服务器自己有 Node：直接在仓库内构建，构建结果已在 frontend/dist，无需 rsync
cd ../frontend
npm ci
npm run build

#    B. 本地 / CI 构建：在本地/CI机器项目根目录执行，不要在服务器执行
#       rsync -a frontend/dist/ ubuntu@<服务器>:/var/www/inuwiki/frontend/dist/

# 6. 重载
cd /var/www/inuwiki
sudo systemctl reload php8.2-fpm
```

### 5.3 从本地 / CI 发布目录同步（不要在服务器 Git 仓库内执行）

以下命令必须在**本地或 CI 的项目根目录**执行，不能在服务器 `/var/www/inuwiki/backend` 目录执行。

```bash
# 1. 本地 / CI 构建前端（子 shell 不改变当前目录）
(cd frontend && npm ci && npm run build)

# 2. 同步后端代码；生产配置与运行时目录不得被覆盖
sudo rsync -a \
  --exclude=runtime \
  --exclude=.env \
  --exclude=config/myconfig.php \
  backend/ /var/www/inuwiki/backend/

# 3. 同步前端产物
sudo rsync -a frontend/dist/ /var/www/inuwiki/frontend/dist/

# 4. composer.lock / composer.json 有变化时安装依赖
cd /var/www/inuwiki/backend
composer install --no-dev --optimize-autoloader

# 5. 数据库结构变更时执行
php think migrate:run
php think migrate:status

# 6. 权限 / 目录同步逻辑变更时执行；常规更新由 crontab 负责
php think kb:subject-sync

# 7. 仅在新增图片归属逻辑或历史图片异常时执行，命令幂等
php think kb:asset-bind

# 8. 重载 PHP-FPM（关键，不能漏）
sudo systemctl reload php8.2-fpm

# 9. 若修改了 Nginx / Supervisor 配置
sudo nginx -t && sudo systemctl reload nginx
sudo supervisorctl restart kb-worker:*
```

重要说明：

- `backend/runtime` 必须排除，避免覆盖生产日志、缓存与上传状态。
- `.env` 与 `config/myconfig.php` 是生产配置，禁止整包覆盖。
- 如果新版本 `myconfig.php` 增加了配置键，需手工对比并补到生产文件，不要直接用仓库版本覆盖。
- 只同步 `backend/` 不会更新前端功能；历史版本差异、操作日志对象类型、用户 ID 展示、工具栏固定、磁盘统计页脚等都在 `frontend/dist` 中。
- 队列代码（`app/job/`、`app/service/` 中上传处理逻辑）变更后，需要重启 `kb-worker:*`。

### 5.4 按变更类型选择

| 变更类型 | 必做步骤 |
|---|---|
| 仅前端 | 构建 `dist` → rsync `frontend/dist/` → 强刷浏览器验证 |
| 仅后端业务代码 | rsync backend → `composer install`（依赖变化时）→ reload PHP-FPM |
| 含数据库迁移 | 备份数据库 → rsync backend → `php think migrate:run` → `migrate:status` → reload PHP-FPM |
| 含队列 / 转码逻辑 | 同步 backend → reload PHP-FPM → `supervisorctl restart kb-worker:*` |
| 含 Nginx 配置 | 备份配置 → 替换配置 → `nginx -t` → reload Nginx |
| 含新配置键 | 手工合并 `myconfig.php` → reload PHP-FPM → 验证公开配置接口 |

### 5.5 更新后验证

```bash
# 取 token
TOKEN=$(curl -s -X POST http://<host>/kbapi/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<pwd>"}' | jq -r .data.token)

# 后端新代码是否已生效：检查新增统计接口
curl -s -H "Authorization: Bearer $TOKEN" \
  http://<host>/kbapi/admin/kb/stats | jq .

# 检查操作日志接口
curl -s -H "Authorization: Bearer $TOKEN" \
  'http://<host>/kbapi/admin/operation-logs?page=1&size=1' | jq .

# 检查迁移状态
cd /var/www/inuwiki/backend && php think migrate:status
```

页面人工检查：

- 登录 WIKI，确认不再停留在旧页面。
- 知识管理页脚显示真实磁盘容量、转码数量、失败数量。
- 操作日志“对象 / 空间”列显示对象类型。
- 阅读页历史版本差异展示正常。
- 长文编辑工具栏保持可见。
- 如果本次涉及权限或空间，确认受限空间数据只对该空间可见用户展示。

验证通过后删除本机临时构建产物即可；生产机上的 `.prev.$TS` 备份建议至少保留一个发布周期。

## 6. 回滚

### 6.1 代码回滚

```bash
sudo rm -rf /var/www/inuwiki/backend
sudo mv /var/www/inuwiki/backend.prev /var/www/inuwiki/backend

sudo rm -rf /var/www/inuwiki/frontend/dist
sudo mv /var/www/inuwiki/frontend/dist.prev /var/www/inuwiki/frontend/dist

sudo systemctl reload php8.2-fpm     # 版本按实际替换，如 php8.5-fpm
sudo nginx -t && sudo systemctl reload nginx
sudo supervisorctl restart kb-worker:*
```

### 6.2 配置回滚

```bash
sudo cp /etc/nginx/conf.d/inuwiki.conf.bak /etc/nginx/conf.d/inuwiki.conf
sudo nginx -t && sudo systemctl reload nginx
```

### 6.3 数据库回滚

`php think migrate:rollback` 默认只回滚最近一次迁移，不要把它当作全库回滚使用。当前迁移中包含：

- 新增字段；
- 注册 / 删除权限；
- 创建分区表；
- 删除 `object_type` 字段；
- 删除 `operation_log` 表。

回滚前先执行：

```bash
php think migrate:status
```

并按版本逐条确认影响。回滚 `20261116001000` 会删除 `object_type` 字段；回滚 `20261116000700` 会删除 `operation_log` 表。

## 9. 常见问题

### 9.0 首次部署故障速查（按现象定位）

| 现象 | 根因 | 处理 |
|---|---|---|
| `Failed opening required .../vendor/autoload.php` | 漏跑 `composer install` | 见 2.3，先在 backend 目录装依赖 |
| `could not find a composer.json file in /root` | 在错误目录执行 composer | cd 到 backend 再执行 |
| Composer 满屏 `Deprecated` / `E_STRICT deprecated` | 系统旧版 Composer + PHP 8.4/8.5 | 无害可忽略，或按 2.2 换官方版 |
| `vendor does not exist and could not be created` | 当前用户对项目目录无写权限 | chown 到部署用户后重试（2.3） |
| 迁移卡在 `SeedKbPermissions`，报 1044 | 迁移要写 `inue_permission`，只读账号写不了 | 临时切可写账号（3.1.1 / 4.3） |
| 后续迁移全 `down`、`kb_subject` 表不存在、`subject-sync` 报 1146 | 上一条没解决，链式失败 | 修复账号后重跑 `migrate:run`，别跳迁移 |
| `sudo mysql` 报 `ERROR 1045 ... using password: NO` | root 已改为密码认证 | 用 `sudo mysql -u root -p` |
| `cp: cannot stat 'deploy/nginx/...'` | 在 backend 里执行，deploy 在根目录 | cd 到项目根目录再 cp（4.4） |
| FPM 起不来 / socket 被占 | inuwiki 池与 www 池监听同一 socket | 给 WIKI 独立 socket（4.4） |
| `/etc/supervisor/conf.d/` 不存在 | 没装 supervisor | `sudo apt install -y supervisor` |
| `supervisorctl status` 报 `PermissionError ... xmlrpc.py` | 权限不足 | 用 `sudo supervisorctl status` |
| 页面 404 但 `Server: Apache/2.x` | 对外端口被 Apache 占用，nginx 未生效 | 换端口或停 Apache，`ss -tlnp` 确认 |
| 首页 200 但所有 `/kbapi/*` 接口 404 | Nginx 没用 `s` 参数传 ThinkPHP 路由 | 按 4.4.1 用 `rewrite ... ?s=...` |
| 首页 403 / 空白、`index.html` 不存在 | 前端 dist 没同步到服务器 | 按 2.3 用 rsync/scp/临时分支分发 dist |
| 形态 B 下资源 404、`/assets/...` 找不到 | 前端未按子路径构建 | `npm run build -- --base=/kb/`（见形态 B） |
| `Could not open input file: think` | 不在 backend 目录执行 | 先 `cd backend` |
| 登录提示「密码错误」 | WIKI 复用 EIP 账号，密码不是 WIKI 自己的 | 用 EIP 门户（8080）同一账号密码；连续失败 5 次锁定 15 分钟，可 `redis-cli DEL login_fail:<用户名>` |
| 点「下载附件」总是跳回登录页；正文图片不显示 | HTTP 站点下资源票据 cookie 带了 `Secure` 被浏览器丢弃 | 见 9.12；升级到含修复的版本并 reload PHP-FPM |
| 视频上传后一直转码中 / `failed` | 未装 ffmpeg，或 `upload.root` 与 nginx `/internal-media/` alias 不一致 | `apt install ffmpeg`；`upload.root=/data/inuwiki`，与 alias 严格一致，改完 reload |

### 9.1 发版后仍是旧页面

按顺序检查：

1. 是否同步了 `frontend/dist/`；
2. 是否执行 `sudo systemctl reload php8.2-fpm`；
3. 浏览器是否强刷；
4. Nginx 是否仍指向旧目录。

### 9.2 操作日志为空

检查：

```bash
php think migrate:status
ls -R /var/www/inuwiki/backend/runtime/oplog
sudo mysql -e "SELECT COUNT(*) FROM Inuwiki.operation_log;"
```

未执行迁移时接口会自愈建表，且无数据时会写一条 `kb.oplog.init`；但规范部署仍必须执行迁移。

### 9.3 操作日志 IP 是 127.0.0.1

检查链路：

1. Nginx `location = /kbindex.php` 是否保留 `HTTP_X_REAL_IP` / `HTTP_X_FORWARDED_FOR`；
2. 前置代理是否透传这两个头；
3. 前置代理 IP 是否加入 `myconfig.oplog.trusted_proxies`；
4. 修改配置后是否 reload PHP-FPM；
5. 历史日志不会回填，需产生新操作验证。

### 9.4 操作人显示 ID 0

历史登录日志中可能存在 `user_id=0`：登录接口在鉴权前写日志，旧版本没有显式传用户 ID。新版本已修复写入，并在查询时按账号回填展示用 ID。若仍出现，确认后端已 reload 且前端 `dist` 已更新。

### 9.5 媒体 404 或无法拖拽播放

检查：

- `myconfig.media.internal_prefix` 与 Nginx `location /internal-media/` 是否一致；
- Nginx `alias /data/inuwiki/` 与 `myconfig.upload.root` 是否一致；
- `/internal-media/` 是否设置 `internal`；
- Nginx 是否返回 `Accept-Ranges: bytes`。

### 9.6 权限配置不生效

- 角色 / 人员目录来自 `kb_subject` 快照，变更后最多等待一个 `kb:subject-sync` 周期；
- 需要立即生效时执行：

```bash
cd /var/www/inuwiki/backend && php think kb:subject-sync
```

### 9.7 页脚存储容量显示占位

检查：

1. `GET /kbapi/admin/kb/stats` 是否返回成功；
2. PHP 是否禁用 `disk_total_space` / `disk_free_space`；
3. `myconfig.upload.root` 或其已存在祖先目录是否可读；
4. 前端 `dist` 是否为当前版本；
5. `kb_attachment` 表是否可执行计数查询，表不可用时队列数字会降级为 0，但磁盘容量仍应显示。

### 9.8 登录提示「账号或密码错误」

WIKI 不自建用户，登录直查 EIP 库 `INUEIP.inue_user`，用 bcrypt（`password_verify`）校验。**必须用 EIP 门户（8080）的同一账号密码**。按顺序排查：

1. **账号是否被锁**：连续失败 5 次锁定 15 分钟（`login_fail:<用户名>` 缓存在 Redis）。清锁：

```bash
redis-cli KEYS "login_fail:*"
redis-cli DEL "login_fail:admin"
```

2. **账号在 EIP 库是否存在/正常**：

```bash
sudo mysql -u root -p -e "
SELECT id, username, status, deleted_at,
       LEFT(password_hash,7) AS hash_prefix, LENGTH(password_hash) AS hash_len
FROM INUEIP.inue_user WHERE username='admin';
"
```

   - 无结果 → 用户名不对（可能叫 `administrator` 等）；
   - `status != 1` → 账号被禁用；
   - `deleted_at` 非空 → 软删除，查不到；
   - `hash_prefix` 应以 `$2y$`/`$2b$` 开头、`hash_len=60`（bcrypt）。若不是 bcrypt，`password_verify` 会失败，需从 EIP 侧重置密码。

3. **最可靠**：在 EIP 门户（8080）重置该账号密码，再用新密码登 WIKI。EIP 库必须是只读账号连接（见 3.1.1），但这里只做查询。

### 9.9 前端产物如何分发到部署机

`dist/` 被 `.gitignore` 忽略，`git pull` 不会带下来。三种方式任选：

1. **部署机本地构建**（有 Node 时最省事）：`cd frontend && npm ci && npm run build`；
2. **rsync / scp**：从构建机推 `frontend/dist/` 到部署机（需配好 SSH 密钥，否则 `Permission denied (publickey,password)`）；
3. **临时分支中转**（scp 不通时）：本地建分支强制提交 dist → 推送 → 部署机只检出 dist 目录：

```bash
# 本地（构建机）
git checkout -b deploy/dist-YYYYMMDD
git add -f frontend/dist
git commit -m "chore(deploy): 临时提交 dist 用于部署"
git push -u origin deploy/dist-YYYYMMDD
git checkout main                       # 切回，不污染主分支

# 部署机：只检出 dist，不动 .env / myconfig.php
cd /path/to/INUWIKI
git fetch origin deploy/dist-YYYYMMDD
git checkout origin/deploy/dist-YYYYMMDD -- frontend/dist
git reset HEAD frontend/dist            # 从暂存区移出，保留工作区文件
chmod -R a+rX frontend/dist
ls -l frontend/dist/index.html          # 确认到位
```

用完可删临时分支：`git push origin --delete deploy/dist-YYYYMMDD`。

### 9.10 `myconfig.php` 被 git 标记为已修改

生产环境的 `myconfig.php` / `.env` 是本地配置，与仓库版本不同是正常的，**不要提交、也不要用 git pull 覆盖**。更新流程中若 `git pull` 报错，按 5.2 先备份再合并。检查改动是否是你预期的生产配置即可。

### 9.11 多 PHP 版本共存时的选择

一台机器装有 8.1/8.2/8.5 多个 FPM 是常见情况。原则是**一条链路统一版本**：CLI（`php -v`）、Nginx `fastcgi_pass` 指向的 socket、supervisor 的 `/usr/bin/php`、以及扩展（`php -m`）要落在同一个装齐了 `pdo_mysql/redis/mbstring` 的版本上。哪个版本扩展齐全就用哪个，不必拘泥文档示例里的 8.2。

### 9.12 下载附件跳回登录页 / 正文图片不显示（Secure cookie）

**现象**：能登录、能上传，API 都正常，但点文章里的「下载」总是 302 回登录页，正文 `<img>` 也不显示。

**根因**：`<a href>` 下载和 `<img>` / `<video>` 由浏览器直接发起，**无法携带 `Authorization` 头**，只能靠登录时下发的 HttpOnly 资源票据 cookie `kb_asset`（见 `Auth::login` 与 `AuthCheck::isMediaResource`）。旧版按 `deploy.env === 'production'` 无条件给该 cookie 加 `Secure`；若站点是 **HTTP**（如 `http://IP:8081`、未上证书的内网生产环境），浏览器会**直接丢弃** Secure cookie，票据从未存下，于是媒体请求被判未登录，`auth_expired_response()` 对文档导航返回 302 到 `/login`。

XHR 走 `Authorization: Bearer`，不受影响——所以会出现"接口全正常，只有下载/图片坏"的特征性表现。

**修复**：`Auth::assetCookie()` 改为按**本次请求实际协议**决定是否加 Secure（`$this->request->isSsl()`），不再依据 `deploy.env`。框架 `isSsl()` 已兼容 `HTTPS` / `REQUEST_SCHEME` / `SERVER_PORT` / `HTTP_X_FORWARDED_PROTO`，HTTPS 部署（含 TLS 在反代终止）仍会加 Secure。

配套要求：Nginx 的 `location = /kbindex.php` 保留 `include fastcgi_params;`（该文件已提供 `REQUEST_SCHEME` 与 `HTTPS`），框架据此识别真实协议，直连 HTTP / HTTPS 都正确。

仅当 **TLS 在更前置的反向代理终止** 时，Nginx 看到的 `$scheme` 是 `http`，需额外透传可信的 `X-Forwarded-Proto`：

```nginx
# 前置代理必须覆盖该头，不能让客户端伪造；仅在确认可信代理后加这一行
fastcgi_param HTTP_X_FORWARDED_PROTO $http_x_forwarded_proto;
```

不要无条件写 `fastcgi_param HTTP_X_FORWARDED_PROTO $scheme;`——反代场景会把 `https` 覆盖成 `http`；也不要直接信任客户端自带的该头，否则 HTTP 站点可能被诱导误判为 HTTPS，cookie 重新带上 Secure 而复现本问题。

**验证**：

```bash
# 1. 登录后看 Set-Cookie：HTTP 站点不应出现 Secure
curl -si -X POST http://127.0.0.1:8081/kbapi/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"<pwd>"}' \
  | grep -i set-cookie

# 2. 带票据请求媒体接口，应返回 200 而非 302
curl -si -H "Cookie: kb_asset=<上一步的票据值>" \
  http://127.0.0.1:8081/kbapi/articles/1/media/2 | head -10
```

改完代码必须 `sudo systemctl reload php$FPM_VER-fpm`（OPcache `validate_timestamps=0`，不 reload 仍是旧代码），然后**重新登录**一次让浏览器写入新 cookie。

> 安全说明：HTTP 站点不加 Secure 是必要的可用性取舍；正式对外服务应启用 HTTPS，届时 cookie 自动带 Secure。
